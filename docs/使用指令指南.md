# 写作与知识库：使用指令指南

## 新增：聊天先保存金字塔主题，再启动写作

聊天入口现在强制多一步。你可以直接说：

> 请把当前聊天中关于【主题】的讨论按金字塔提炼：先定核心命题，再横向分组、纵向展开。每个论点附具体对话素材、支持关系、材料性质和出处，保留关键模型，缺少论据的地方明确留缺口。将 Markdown 保存到 writing/topic，给我文件链接，然后用该文件启动写作；先让我确认大纲，成稿确认后保存，发布另行确认。

只想积累主题时，将最后一句改为“只保存主题供我查看，先不要启动写作”。

外层 agent 的调用顺序是 `writing_topic_guide` → 读取实际聊天并提炼 → `writing_prepare_topic` → 展示文件 → `writing_start(topic_file=返回路径)`。后文聊天示例均先执行此步骤，不能再直接把观点或原聊天传入 writing_start 的 idea。

主题文件可在终端使用（替换成实际返回路径）：

```powershell
Set-Location '<writing 项目目录>'
uv run python main.py --topic-file 'topic/实际主题文件.md'
```

这会从文件读取主题和提炼结果，不再次询问主题/想法。旧的普通材料文件不直接当作提炼结果，应先让 agent 按模板整理另存，原文件保留。聊天派生任务使用这个入口；下文不带 --topic-file 的交互命令适用于手工输入场景。

以下按当前代码核对（2026-09-07）。聊天示例是发给 agent 的自然语言；PowerShell 代码块是复制到终端执行的命令。聊天入口需已连接对应的 writing / llm_wiki MCP 服务（让 agent 能调用本地流程的接口）。若看不到对应工具，使用终端入口，不要把普通聊天生成的文章误认为已经经过本管道。

## 1. 第一次写文章：从这组命令开始

打开 PowerShell，进入写作目录：

```powershell
Set-Location '<writing 项目目录>'
uv run python -m tools.doctor
uv run python main.py --topic-id agent-data-science
```

doctor 检查路径、规范文件等基础配置，不证明模型密钥、联网检索或实际生成都已成功。正常写作会使用配置的模型与搜索服务。

程序问“文章主题”时，输入一行，例如：

```text
利用 Agent 做数据科学项目，为什么要先明确验收标准
```

程序问“你的思路/方向/想法”时，可连续输入多行，最后单独输入 END：

```text
我的观点：Agent 的价值取决于任务拆解、证据与验收标准，而不只是模型能力。
读者：有 Python 基础、准备使用 Agent 做数据分析的人。
请保留我的观点，主动寻找反例；涉及最新能力时核对一手资料。
我的已有材料：
@topic/利用agent做数据科学项目的要点.md
END
```

随后按屏幕提示操作：

| 停下来的位置 | 你输入什么 | 接下来发生什么 |
|---|---|---|
| 大纲确认 | 回车或 `y` | 按该大纲搜证、写稿 |
| 大纲不满意 | 直接输入修改意见 | 修改大纲，再请你确认 |
| 最终稿确认 | `1` | 确认文章无误并保存本地，尚未发布 |
| 内容或论据有问题 | `2`，然后输入反馈，以 `END` 结束 | 回到写作环节重写，再审核 |
| 表达不自然 | `3`，然后输入反馈，以 `END` 结束 | 重新润色，再核验 |
| 保存后的发布预览 | 回车 | 仅保留本地稿件 |
| 保存后的发布预览 | `发布` | 同意将预览中的版本推送到预览中的 GitHub 目标 |

有未解决的质量问题时，允许保存本地，但发布检查会阻止推送，需要先修正。默认博客路径已配置，真实稿保存后会尝试展示发布预览，不必额外加 `--push`。

## 2. 终端模式速查

以下命令均在 `<writing 项目目录>` 执行。

| 你要做什么 | 命令 | 注意事项 |
|---|---|---|
| 正常写一篇 | `uv run python main.py` | 确认大纲、确认成稿、单独确认发布 |
| 同一主题写系列文章 | `uv run python main.py --topic-id agent-data-science` | 每次新建一篇，复用该主题的长期记忆 |
| 熟悉流程、测试按钮 | `uv run python main.py --mock` | 不调用真实模型或搜索；测试稿不能发布，仍会写本地测试会话和输出 |
| 查看 CLI 历史会话 | `uv run python main.py --list` | 复制输出中的会话 ID |
| 中断后继续原来那篇 | `uv run python main.py --thread-id 实际会话ID` | 已完成节点不用从头跑；未完成节点可能重新执行 |
| 查看或修改已完成的那篇 | `uv run python main.py --thread-id 实际会话ID` | 查看模式中 `1` 是退出，`2/3` 是重写/重润色 |
| 明确要求保存后进入发布预览 | `uv run python main.py --push` | 会启动/继续写作流程；它不是免确认发布，也不是“发布任意旧文件”命令 |
| 查看参数 | `uv run python main.py --help` | 当前支持的参数以此为准 |

`topic-id` 是“这一组文章属于哪个主题”，如 `agent-data-science`；`thread-id` 是“继续哪一次写作”。同主题写新文章用前者，继续旧文章用后者。主题标识只用小写英文字母、数字、连字符，最多 64 个字符；续跑已有会话时沿用存档身份，传新主题标识不会把旧会话迁移到新主题。

## 3. 在聊天里下指令

前提：当前聊天已连接写作 MCP 服务，能调用 `writing_start` 等工具。服务后台运行，启动后返回任务 ID；保留它，以便查询、修改或发布。这里的任务 ID 与 CLI 的会话 ID 不同；`--list` 不是所有 MCP 任务的总列表。

### 标准写作：大纲也由你确认

直接发给 agent：

```text
请调用 writing 管道写一篇文章。
主题：利用 Agent 做数据科学项目，为什么要先明确验收标准。
主题标识：agent-data-science。
我的观点：模型能力只是基础，任务拆解、证据和验收标准决定最终效果。
先把大纲交给我确认（auto_approve=false），再搜证写稿。
成稿后让我审阅；我确认无误后才保存，保存后再单独问我是否发布。
```

有文件时追加“请先读取 <writing 项目目录>\topic\利用agent做数据科学项目的要点.md，把内容作为作者材料传给管道”。MCP 的 `idea` 参数不会像 CLI 一样自动展开 `@文件`，需由外层 agent 先读取实际内容。

### 快速出稿：省去大纲确认

```text
请用 writing 管道写【文章主题】，我的观点是【观点】。
主题标识为 agent-data-science。大纲自动通过（auto_approve=true），直接推进到成稿审阅。
最终稿必须让我确认后才保存；保存后再单独询问发布。
```

这里只省掉一次大纲交互，检索、审核和成稿核验仍运行，不意味着模型更快或审核更少。CLI 目前没有 `--auto-approve` 参数。

### 查询、修改、保存和发布

把下列“实际任务ID”替换为启动时返回的值：

| 场景 | 发给 agent 的指令 |
|---|---|
| 查询进度 | `查询 writing 任务【实际任务ID】的进度；若正等我审核，展示待审内容。` |
| 修改大纲 | `任务【实际任务ID】的大纲不通过：先讲一个实际失败案例，再解释验收标准。` |
| 重写内容 | `任务【实际任务ID】的成稿内容需修改：第三部分缺少反例，请补足论据并重写。` |
| 重润色 | `任务【实际任务ID】的成稿需要重润色：删掉空泛总结，保留数字、来源和限定条件。` |
| 确认保存 | `我确认任务【实际任务ID】当前展示的文章无误，同意保存本地，暂不发布。` |
| 取本地稿件 | `展示 writing 任务【实际任务ID】已保存的稿件和文件路径。` |
| 发布前预览 | `请展示任务【实际任务ID】已保存版本的发布预览，先不要发布。` |
| 预览后同意发布 | `我同意把刚才预览的文章版本发布到预览中的 GitHub 仓库和分支。` |
| 故障后续跑 | `故障已解决，请从检查点继续 writing 任务【实际任务ID】，不要新建任务。` |

修改大纲/成稿适用于任务正在对应人工确认点等待时。MCP 当前不支持直接把 completed 任务 resume 回修改状态；已完成稿件要回访修改，可查其 `thread_id` 后用 CLI 回访，或以稿件为材料新建同主题任务。若使用 CLI 回访，完成状态应以 CLI 新输出为准，旧 MCP 任务记录不会自动同步更新。

## 4. 引用自己的材料

CLI 的“想法”和“反馈”输入支持：

```text
@topic/利用agent做数据科学项目的要点.md
```

也可以把相关材料放到同一目录后输入 `@topic`，程序会读取该目录的文本文件。目录较大时优先指定文件，避免带入无关内容。PDF、图片等二进制文件会跳过；PDF 要先转成 md/txt 再用这个入口引用。文件选择不等于自动认可其中观点，想保留什么、允许挑战什么，应在输入里说明。

三个新增 skills 已自动加载，不必每篇再手动点名。特殊表达要求写在作者材料或反馈里即可，例如“先给一个具体案例，再解释原理；保留我的个人判断，事实与推断分开表述”。

## 5. 知识库的使用方式

先切换目录：

```powershell
Set-Location '<llm_wiki 项目目录>'
```

### 查询已有资料

可直接打开本库 `wiki/index.md` 查阅。已连接知识库服务时，发给 agent：

```text
请用 kb_query 查询知识库里关于 Agent 评估和验收标准的资料，列出相关笔记路径、主要观点和待验证问题。这次只查询，不写文章。
```

这是查已有知识，不是实时全网搜索。

### 收藏一篇文献

终端执行时，把示例 URL 换成实际来源；先预览再执行：

```powershell
uv run python scripts/ingest_source.py 'https://example.com/实际文章' --dry-run
uv run python scripts/ingest_source.py 'https://example.com/实际文章'
```

支持 URL、arXiv ID、DOI、本地文件。脚本先保存原文并建立草稿，不会单靠这一步生成完整阅读笔记。之后让知识库 agent “按 prompts/ingest_source.md 完善刚入库的草稿”。已连接知识库服务时，也可直接说“请用 kb_ingest 把【实际来源】入库，保留原文并整理草稿”；该服务会编排入库与笔记整理。

### 更新候选与每周阅读清单

```powershell
uv run python scripts/fetch_candidates.py --source all --limit 20 --dry-run
uv run python scripts/fetch_candidates.py --source all --limit 20
uv run python scripts/weekly_update.py --limit 20 --dry-run
uv run python scripts/weekly_update.py --limit 20
```

前两条抓候选，后两条筛选已有候选并生成清单。fetch 的 limit 是每页数量，会自动翻页；weekly_update 的 limit 是本次最多处理多少条候选。fetch 的 dry-run 仍会联网，只是不保存数据。

需要完整周更（包含 Kimi 整理）时，使用下面这一组替代上面的分步操作，需已配置 Kimi CLI：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/weekly_compile.ps1 -DryRun
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/weekly_compile.ps1
```

查看 `data/review_queue/` 中新清单；在知识库的 Kimi 交互会话中说“带我过一遍本周待复核清单”。有推荐结果不等于已经人工确认。

### 检查知识库与重试写作资料回库

```powershell
uv run python scripts/lint_wiki.py
uv run python scripts/compile_index.py
```

第一条只体检，第二条重建索引。正常写作确认保存后自动回库；只有日志提示回库失败时，才用实际证据包路径重试：

```powershell
uv run python scripts/import_writing.py 'D:\实际稿件目录\evidence.json' --dry-run
uv run python scripts/import_writing.py 'D:\实际稿件目录\evidence.json'
```

## 6. 当前边界与结果位置

- 没有独立的 `--research-only`、`--deep`、`--fast` 或“完全自动免审发布”参数。只搜资料后停下，目前需要另行交给 agent 执行，不能声称是已有写作管道模式。
- `--mock` 是模拟数据；知识库 `--dry-run` 是预览写入动作，部分命令仍联网，两者不同。
- 本地文章位于 `<writing 项目目录>\output\日期-主题-运行标识\版本标识\article.md`；同目录 `reading.md` 是待读来源，`evidence.json` 是证据包。
- GitHub 目标目前为 `ac0033/ac0033` 的 `main` 分支、`articles/` 目录；实际预览为准。推送成功不等于另有网站已经完成部署。
- 保存后直接手改 article.md 会使已确认指纹失效，不能沿用旧发布许可；需重新审阅保存，再预览并确认发布。
- 命令 `uv run python -m service.writing_server` 和知识库的 `uv run python -m service.kb_server` 是给 MCP 客户端配置的服务启动命令，不是手动输入文章的聊天窗口。要从终端直接写文章，使用 `main.py`。

维护依据：writing/main.py 的参数和交互、service/writing_server.py 的工具接口、tools/identity.py 的主题标识规则，以及 llm_wiki/scripts/ 和 service/kb_server.py 的实际入口。

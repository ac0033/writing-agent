# 从"时灵时不灵"到"敢放手自动跑"，构建可靠 Agentic Workflow 的三层纵深防御

## 一、Agent 为什么不可靠，这是个系统工程问题

如果你正在把 LLM Agent 从 demo 推向生产，大概率被三个问题折磨过。

**时灵时不灵。** 同一个任务，今天跑通了，明天换一句话就崩。你换了 prompt、调了温度、甚至换了模型，好了两天，又坏了。

**出了错不知怎么回事。** Agent 给了一个离谱的输出，你盯着屏幕想搞清楚它到底哪一步走歪了，却发现除了最终结果，中间什么也没留下。

**不敢放手自动跑。** 逻辑上你知道它"应该"能跑通，但你就是不敢把最后那个"确认执行"的按钮从人工改成自动。因为你没法回答一个问题：它会不会在某个我没想到的角落闯祸？

很多人本能地把这三件事归因于模型不够强。但证据指向另一个方向。

一篇覆盖 2020 至 2026 年 LLM Agent 系统的综述给出了一个关键公式：智能体质量，包括成功率、效率、安全性和泛化性，产生于**模型能力、运行时基础设施（harness）、任务结构和评测设计**四者的交互（[From Question Answering to Task Completion: A Survey on Agent System and Harness Design](https://arxiv.org/abs/2606.20683)）。四个因素相乘，任何一项趋近于零，整体就趋近于零。而模型恰恰是四者当中你唯一没法直接优化的黑盒，你改不了权重，改不了训练数据，只能选一个版本然后接受它。其余三个，harness 怎么搭、任务怎么切、评测怎么设计，全都攥在工程师手里。

两条实证把这件事钉得很死。

第一条来自 SWE-agent。普林斯顿团队不换模型、不微调，只重新设计了智能体与计算机之间的交互接口，他们称之为 ACI（Agent-Computer Interface，智能体-计算机接口），涵盖命令格式、文件编辑方式、搜索结果呈现等，就在 SWE-bench 上拿到了显著的性能提升（[SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering](https://arxiv.org/abs/2405.15793)）。模型还是那个模型，变的是模型看到什么、能做什么、怎么得到反馈。

第二条来自 AgentBench。在这个评估 LLM 作为智能体能力的基准套件中，相当一部分失败，比如格式解析错误、在同一个动作上循环打转，根源在于运行时的解析兜底和循环检测没有接住，模型本身有能力做对（[AgentBench: Evaluating LLMs as Agents](https://arxiv.org/abs/2308.03688)）。harness 没兜住，锅就不该全扣在模型头上。

两条证据合在一起，工程判断就清楚了：**可靠性的瓶颈在模型之外。**

承认这一点之后，很多团队会掉进三个错误本能。

- **换更强的模型。** 贵且慢，而且新模型会引入新的失败模式，你只是换了一种"时灵时不灵"。
- **HITL（Human-in-the-Loop）万能。** 每一步都让人确认，确实安全，但 Agent 退化成了"高级自动补全"，自动化的意义归零。
- **把权限和规则写进 prompt。** "你不能删除文件""你必须先确认"，这些自然语言约束在模型眼里只是"建议"，一次幻觉就穿透了。

正确的思路是**纵深防御**。三层墙，每层再设三道防线，预防、检测、恢复。单 Agent 层治好"记不住、说不清"；多 Agent 层查清"锅在谁身上"；系统层把"主动性"关进笼子。接下来先定验收标准，再逐层拆解。

## 二、四个设计目标，透明 → 可控 → 直观 → 自动化

治这个病，先定验收标准。这一节只画地图，不展开。每个目标在后面三层都有具体机制兑现，这里只说它是什么、怎么检验它做到了。

四个目标有因果链，一层托着一层。

**透明是前提。** 看不到 Agent 在想什么、为什么这么做，后面一切管控都是盲人摸象。检验标准就一句话：出了事，你能不能在五分钟内答出"它当时为什么这么做"？后文的兑现机制是 thinking.md 全量落盘。

**可控是手段。** 看到了还不够，得能拦住、能熔断、能让它在不确定时停下来，而不是硬闯。检验标准：当 Agent 遇到超出预期的情况，它是先斩后奏，还是先奏后斩？兑现机制是 fail-closed 审核门。

**直观是让"可控"可被人类理解。** 权限规则如果只存在于代码里，运维人员看不懂、不敢改，那"可控"就是纸面的。检验标准：一个新同事能不能在十分钟内看懂这个 Agent 现在能做什么、不能做什么？兑现机制是信任阶梯一眼可见。

**自动化是前三项都达标后挣来的。** 它排在最后。检验标准：你敢不敢在周五下午部署一个无人值守的定时任务？兑现机制是信任逐级解锁。

地图画完了。下面进入第一层。

## 三、第一层·单 Agent，把"记不住、说不清"治好

### 一个场景切入

想象这样一个场景。你在和 Agent 协作写代码，中途你改了一个架构决策，"不用 Redis 了，换成本地缓存"。这条决策变更，Agent 得记住，不然下次会话又给你生成 Redis 代码；还得说清楚，不然你问"为什么用本地缓存"，它答不上来。上下文一长，这条决策还不能被淹没丢掉。

一个失忆的、失焦的 Agent，后面所有防线都白搭。多 Agent 协作时它传错信息，系统层监控时它给不出决策依据。记忆是单 Agent 可靠性的地基。

### 四层记忆，各管各的

agent-memory 系统把记忆分成四层。**prompt 快照**存当前对话的原始上下文，**短期记忆**存本次会话的临时状态，**工作记忆**存当前任务的关键决策和约束，**长期记忆**存跨会话沉淀的事实和偏好。每层有明确的"谁写、谁读、什么时候淘汰"，不混用。

### 写入路径、三层数据分离、token 水位摘要

**写入路径，一条信息要过三道关才能入库。**

Agent 决定"这条信息值得记住"之后，并不能直接写进记忆库。写入路径上有三道门。

第一道，**脱敏**。原始对话里可能包含 API key、密码、用户隐私。写入前必须先剥离敏感信息。这一步是硬编码的前处理，代码在模型输出之后、存储之前自动执行，模型没有机会"忘记"脱敏。

第二道，**蒸馏**。原始对话往往冗长、重复、夹杂无关信息。蒸馏步骤把一段对话压缩成一条结构化的记忆条目，事实是什么、适用范围是什么、置信度多高。这一步由模型完成，但输出格式被 schema 约束，固定字段，不接受自由文本。

第三道，**对账**。新写入的记忆和已有记忆可能冲突，比如旧记忆说"用 Redis"，新记忆说"用本地缓存"。对账步骤检测冲突，标记旧条目为"待修订"或"已失效"，不会默默覆盖。

三道关全过，才落盘。任何一道失败，写入中止，原始信息保留在 raw 层等待人工处理。

**三层数据分离，raw / memory / index。**

这三层的关系，用数据库来类比最直观。**raw 层是只追加的原始日志**，相当于数据库的 WAL（Write-Ahead Log），只进不改，是最终的审计依据。**memory 层是唯一事实来源**，相当于经过 ETL 清洗后的主表，所有读取都走这里。**index 层是可重建的缓存**，相当于数据库索引，丢了可以从 memory 层重新生成，不影响数据完整性。

为什么要这么分？因为 Agent 会犯错。如果只有一层存储，Agent 一次错误写入就可能污染所有历史。三层分离意味着 raw 永远在，memory 可以修正，index 可以随时重建。最坏情况下，你可以从 raw 层完整重放，恢复出正确的 memory。

**token 水位摘要，油箱预警线。**

LLM 的上下文窗口是有限的。对话越来越长，上下文逼近容量上限时，必须做摘要压缩。但压缩本身有损，可能丢掉关键信息。

agent-memory 的做法是设一条"水位线"：已用 token 达到上下文窗口的 20% 时，触发摘要流程。摘要不是简单地"把前面的对话缩成一段话"。摘要前有一个**抢救步骤**，先把工作记忆中的关键状态（当前任务目标、未完成的决策、用户显式约束）提取出来，确保它们不会在压缩中丢失。同时，至少保留最近三轮对话的原文不压缩。[研究表明，LLM 对上下文中间位置的信息处理最弱，首尾最强](https://arxiv.org/abs/2307.03172)，最近三轮在"尾部"，恰好是模型最能利用的位置。

打个比方，这就像油箱预警线。还剩 20% 的油就触发"找加油站"的流程，不等到彻底烧完。压缩行李之前，先把护照和钱包掏出来放口袋里。

### 检测与恢复

预防做得再好，也需要检测机制兜底。

- **stale_wm 滞后判定**。工作记忆中的某条信息长时间未被引用或更新，系统标记它为"可能过时"，下次召回时降低优先级或触发确认。
- **对账冲突入队**。写入时的对账发现冲突，不静默丢弃，进入待处理队列，等下一次交互时向用户确认。
- **三档验证一票否决**。记忆条目从短期晋升到长期时，要过三档验证，格式合规、语义一致、与已有知识不矛盾。任何一档不通过，晋升中止。
- **review 门 fail-closed**。验证流程本身出错，比如验证服务不可用，默认行为是"不晋升"。方向永远是 fail-closed，失败时关闭，绝不 fail-open。

恢复机制确保出了问题能回滚。摘要前抢救，前面说了。晋升前快照，晋升长期记忆前先保存当前 memory 层快照，晋升失败可回退。变更传播三分类，一条记忆被修改后，系统自动扫描关联条目，分为"已失效""需修订""不受影响"三类，逐一处理。

### 三条红线

最后，有三条规则是硬编码的，Agent 不能修改、不能绕过。

1. raw 层只追加，永不修改、永不删除。
2. 写入必须过脱敏、蒸馏、对账三关，缺一不可。
3. 评测标准、晋升门槛、审计日志的修改权限不在 Agent 手里。Agent 不能给自己改考卷。

### 场景闭环

回到开头的场景。你说"不用 Redis 了，换本地缓存"。这条决策变更触发写入路径。脱敏，无敏感信息，通过。蒸馏，生成结构化条目，"缓存方案：本地缓存，替代 Redis，原因：用户决策，日期：今天"。对账，发现旧条目"缓存方案：Redis"，标记为"已失效"，新条目入库。工作记忆更新。

如果此时上下文已接近水位线，摘要流程触发。关键状态（包括这条新决策）先被抢救出来，然后旧对话被压缩，最近三轮保留原文。

会话结束，蒸馏步骤把本次会话的关键决策沉淀进长期记忆。下次新会话开始时，系统根据任务上下文召回相关记忆，"缓存方案：本地缓存"会被注入 prompt，Agent 不会再生成 Redis 代码。

闭环完成。一个决策，从产生到持久化到跨会话生效，每一步都有预防、检测、恢复。

## 四、第二层·多 Agent，把"锅在谁身上"查清

先说一件事。你正在读的这篇文章，就是接下来要讲的这条多 Agent 流水线的产物。大纲由人确认，资料由研究 Agent 搜集，初稿由写作 Agent（也就是"我"）生成，审核由审核 Agent 把关，润色由风格 Agent 处理。你不是在读一篇"关于多 Agent 的文章"，你是在读一个多 Agent 系统的输出。

### 多 Agent 的新失败面

单 Agent 的问题是"记不住、说不清"。多 Agent 的问题完全不同，**锅在谁身上？**

一篇对多个流行多智能体框架、150 余条对话轨迹进行系统分析的论文，识别出 14 种细粒度失败模式，归为三大类：规范与系统设计失败、智能体间协调失准、任务验证与终止问题（[Why Do Multi-Agent LLM Systems Fail?](https://arxiv.org/abs/2503.13657)）。说得更直白一点，系统设计时没定清楚"谁该干什么"，这是一类；Agent 之间传话传歪了，这是第二类；没人检查最终结果对不对就交卷了，这是第三类。

这三类失败，在单 Agent 里不存在或很轻微。单 Agent 自己跟自己说话，不存在"传话传歪"。但两个 Agent 之间的接口一旦是自然语言，信息损耗、格式漂移、错误级联就全来了。上游 Agent 输出一个微妙的格式偏差，下游 Agent 可能完全误解语义。最致命的是，你不知道是哪一步出的问题。

### 两段式接口契约 + 工具循环硬预算熔断

writing-agent 流水线用 LangGraph 构建，五个节点：大纲确认 → 资料搜集 → 初稿写作 → 内容审核 → 风格润色。节点分工一句话带过，不展开。这里讲透两个核心机制。

**两段式接口契约，`<scratchpad>` + `<result>`。**

每个 Agent 节点的输出被强制分成两段。`<scratchpad>` 是思考过程，推理、犹豫、取舍、对资料的判断。`<result>` 是正式产出，只有这段会被传递给下游节点。

这个设计解决三个问题。

第一，**上下文隔离**。下游节点只看到 `<result>`，不会被上游的思考过程污染。上游 Agent 在 scratchpad 里写了"我不太确定这个数据"，下游看不到这句话，不会被它的不确定性影响。代码层面，传递逻辑只提取 `<result>` 标签内的内容，`<scratchpad>` 根本不进入下游的 prompt。

第二，**可回溯性**。`<scratchpad>` 不传给下游，但也不丢弃，它被落盘为 thinking.md 文件。任何时候出了问题，你可以打开对应节点的 thinking.md，看到那个 Agent 当时在想什么、为什么做了那个决定。这就是"透明"在多 Agent 层的兑现。

第三，**不依赖模型原生 thinking 格式**。不同模型的"思考链"格式不同，有的用 `<thinking>`，有的用 `reasoning_content` 字段，有的干脆没有。两段式契约是应用层自己定义的，跟模型无关。换模型不需要改解析逻辑。

**工具循环硬预算 = 熔断。**

Agent 在执行任务时可能需要多次调用工具，搜索、读文件、执行代码。如果没有上限，一个陷入循环的 Agent 可以无限调用下去。烧钱是小事，产生大量垃圾上下文污染后续节点是大事。

writing-agent 的做法是设一个硬预算，每个节点的工具调用次数有上限。达到上限，循环强制终止，当前状态保存，节点标记为"超限"。这是代码层面的硬中断，模型没有协商余地。

熔断之后怎么办？也不是直接失败。当前已完成的部分产出被保留，未完成的部分作为"遗留问题"标记，交给后续节点或人工处理。就像电路保险丝，烧断了是隔离故障回路，其余回路继续工作，整栋楼不停电。

### 检测与恢复

**检测**靠三件事。契约校验，下游节点收到输入时先检查格式是否符合 `<result>` 结构，不符合就拒绝处理并报错。审核循环上限，写作→审核→修改的循环最多三轮，超过三轮强制进入终审，带着已知问题交稿。thinking.md 全量落盘，前面说了，任何节点的决策过程都可以事后审查。

**恢复**靠四件事。修复重试，某个节点的输出违反了接口契约，系统自动补一次重试，给模型一个"你格式不对，重新来"的机会。断点续跑，LangGraph 的 checkpointer 机制保存每个节点完成后的状态，系统崩溃或人工中断后，可以从最后一个完成的节点继续，不需要从头跑。超限降级，工具循环超限后，节点降级为"部分完成"状态，遗留问题上报终审页面。记忆集成 fail-open，记忆系统在读取时出错，不阻塞主流程，只是本次没有记忆加持。这里方向是 fail-open，因为记忆缺失的代价远低于流程中断的代价，跟写入时的 fail-closed 形成有意的对比。

### 多模型分工与成本纪律

五个节点不全用同一个模型。粗活（格式校验、简单分类）用便宜快速的模型，关键活（写作、审核判断）用能力最强的模型。有研究指出，评估 Agent 系统时应该同时看准确率和成本，追求两者的 Pareto 最优，而不是只看准确率（[AI Agents That Matter](https://arxiv.org/abs/2407.01502)）。用贵模型做不需要贵模型的事，谈不上"保险"，那是浪费。浪费本身也是一种不可靠，因为它让你无法持续运行。

### 自嘲式收束

你现在读到的这一版文字，可能就经历过审核循环的第 2 轮。审核 Agent 在第一轮指出了某个论据不够充分，写作 Agent（我）改了一版，审核 Agent 才放行。你看到的"流畅"，是契约和熔断在背后兜着。

## 五、第三层·系统闭环，把"主动性"关进笼子

前两层解决的都是"执行人类指令时怎么不出错"。但还有一类更棘手的问题：**Agent 主动干活时，怎么不闯祸？**

反应式 Agent，你说一句它做一句；主动式 Agent，它自己发现问题、自己提方案、自己执行。两者在风险性质上完全不同。反应式的风险是"做错了"；主动式的风险是"做了你根本不知道的事"。用户对前者的容忍度远高于后者。"你帮我做错了"和"你背着我做了"，是两种完全不同的信任破坏。

AIOS 系统要解决的就是这个问题：如何让 Agent 拥有主动性，能自己发现优化机会、提出假设、设计实验，同时不让这种主动性变成失控的风险源。

### 第一性原理：随机性是资产，但必须配上选择机制

先说一个反直觉的判断：随机性是 AIOS 最强的能力。

LLM 的本质是概率采样，这意味着它能产生人类想不到的组合、类比、假设。在一个"发现优化机会"的场景里，这种随机性就是变异，就像进化中的基因突变，大部分没用，但偶尔能产生突破。

但变异本身不是资产。**随机性只有配上选择机制才是资产。** 在进化里，选择机制是自然选择；在 AIOS 里，选择机制是三层。沙箱实验，假设在隔离环境里验证，不碰生产。评估协议，预定义的指标判定假设是否成立。人类反馈，最终由人决定要不要采纳。

纲领三句话：LLM 负责变异，确定性机制负责选择，人类拥有最终否决权。

### 双回路权限位分离 + 假设卡

**双回路，执行回路 vs 自治回路。**

AIOS 把 Agent 的活动分成两条回路，权限位完全不同。

**执行回路**是响应式的。用户下了指令，Agent 执行。这条回路有写权限，可以改文件、调 API、执行部署，但每一步都有 HITL 兜底，关键操作前暂停等确认。

**自治回路**是主动式的。Agent 自己发现"这个配置可能可以优化"、"这个日志模式暗示一个潜在问题"。这条回路**只有只读权限和沙箱权限**。它可以读日志、读指标、在沙箱里跑实验，但不能碰生产环境的任何东西。

用出纳来类比最直观。出纳有只读台账的权限，能看账，但要动钱必须过柜台审批，走执行回路。自治回路就是"看账"，执行回路就是"动钱"。两个回路的权限位是操作系统层面设定的，不写在 prompt 里。prompt 里写"请不要修改生产环境"，一次幻觉就穿透了。

权限位分离让"激发自主性"和"不失控"不再矛盾。你不需要在"让 Agent 主动"和"保证安全"之间二选一。让它主动，但只在只读加沙箱的范围内主动。它闯的最大祸，不过是沙箱里多跑了一个实验，代价可控。

**假设卡，强制可证伪。**

自治回路产生的每一个"想法"，都必须写成一张假设卡。假设卡是结构化模板，必须包含三样东西：假设陈述（"我认为 X 会导致 Y"）、检验方法（"如果做 Z 实验，观察到 W 结果则证实"）、预期影响（"如果成立，收益是什么"）。

关键约束：**没有检验方法的假设，不得进入下一层。** Agent 说"我觉得这个配置可能更好"但说不出怎么验证，这张卡直接被拒。这不是苛刻，是防止"不可证伪的想法"堆积成噪音，淹没真正有价值的假设。

假设卡通过格式校验后，进入沙箱实验阶段。实验是**预注册**的，实验方案、评估指标、成功标准在实验开始前就固定，不允许跑完之后改标准。这防止了"先射箭再画靶"。

### 五组件归位

AIOS 的五个核心组件，按预防/检测/恢复归位。

| 组件 | 归位 | 一句话 |
|------|------|--------|
| 权限层（OS/容器级） | 预防 | 权限不落 prompt，落操作系统和容器配置，模型无法绕过 |
| 观测层 | 检测 | 观测本身也是权限，你能观测到什么，决定了你能对什么做判断 |
| 假设卡 + 可证伪门 | 预防 | 无检验方法的假设不进入实验，从源头过滤噪音 |
| 沙箱孪生 + 预注册实验 | 检测 | 假设在隔离环境验证，评估标准预先锁定 |
| 三不原则 + 打扰预算 | 恢复/预防 | 不主动修改生产、不主动联系外部、不连续打扰用户；打扰有预算上限 |

### 信任阶梯

AIOS 定义了 L0 到 L4 的信任阶梯，Agent 的权限随信任等级逐步解锁。这里不写具体数值阈值，它们因部署环境而异，只说结构。

| 等级 | 定性描述 |
|------|----------|
| L0 | 纯只读，只能观测和报告 |
| L1 | 可在沙箱内执行实验 |
| L2 | 可生成执行方案，但需人工确认后才执行 |
| L3 | 低风险操作可自动执行，高风险仍需确认 |
| L4 | 在明确划定的范围内全自主 |

关键设计：**当前信任到哪一级，一眼可见。** 不藏在配置文件里的一个数字，是 Agent 每次交互时都会声明的状态。用户不需要去翻文档就知道"它现在能做什么"。信任升级不自动，需要累积足够的成功记录，且由人类审批。降级则是即时的，一次严重失误，立刻回落。

### 主动性本身是风险源

最后要点破一个容易被忽略的事实：**主动性本身是风险源，风险不只在"执行方式"上。**

一个反应式 Agent 做错了，用户想的是"它能力不行"。一个主动式 Agent 做了用户不知道的事，用户想的是"它不可信"。后者的信任修复成本远高于前者。

所以 AIOS 在主动性上采取**精确率优先于召回率**的策略：宁可漏掉十个优化机会，也不要在用户没预期时打扰一次。打扰疲劳是主动性的头号死因。Agent 每天弹二十条"我发现了一个可能的优化"，用户第三天就会把它静音，然后永远不再打开。

## 六、全景矩阵，三层 × 预防/检测/恢复

把前三层摊成一张表。这张表的用法是对照你自己的系统，看哪格是空的。

| | 预防 | 检测 | 恢复 |
|---|---|---|---|
| **单 Agent（agent-memory）** | 三层数据分离；写入三关；token 水位摘要 | stale_wm 滞后判定；对账冲突入队；三档验证 | 摘要前抢救；晋升前快照；变更传播三分类 |
| **多 Agent（writing-agent）** | 两段式接口契约；上下文最小够用；工具循环硬预算 | 契约校验；审核 ≤3 轮；thinking.md 落盘 | 修复重试；断点续跑；超限降级；记忆 fail-open |
| **系统（AIOS）** | 权限落 OS 层；假设卡可证伪门；三不原则 | 观测即权限；沙箱预注册实验；打扰预算 | 信任即时降级；沙箱隔离兜底；遗留问题上报 |

四个设计目标的覆盖检查。透明由 thinking.md 落盘加观测层兑现；可控由 fail-closed 门加硬预算熔断加权限位分离兑现；直观由信任阶梯可见加假设卡结构化兑现；自动化由信任逐级解锁加断点续跑兑现。

但这张表真正的价值不在格子本身，在**跨层的五条共性**。它们是不依赖具体系统的工程原则。

1. **权限分层。** 不同职责的组件拿不同的权限，而不是"先给满权限再靠 prompt 约束"。反例：把"不要删除文件"写在 system prompt 里，然后给 Agent 完整的文件系统写权限。
2. **fail-closed 方向。** 不确定时，默认行为是"不做"。反例：验证服务挂了，系统选择"跳过验证直接通过"。
3. **证据链。** 每一步决策都有可回溯的记录，出了事能定位到具体节点、具体原因。反例：只保存最终输出，中间推理过程全部丢弃。
4. **必可回滚。** 任何写入操作都有对应的撤销路径。反例：Agent 直接覆盖生产配置，无快照、无版本历史。
5. **注意力配额。** 上下文是稀缺资源，每个组件能占用的上下文量有预算。反例：把所有历史对话原封不动塞进 prompt，直到窗口溢出。

如果你的系统在某条共性上完全没有对应机制，那一格就是空的。空格往往就是下一次事故的位置。

## 七、总结：自动化是挣来的

回到开头的三个痛点。

**时灵时不灵。** 记忆与自愈机制让 Agent 跨会话保持一致。决策不会丢，上下文不会失控膨胀，关键信息不会被摘要吞掉。"稳"是写入三关、水位摘要、变更传播这些机制砌出来的。

**出了错不知怎么回事。** 证据链和 thinking.md 让每个节点的决策过程可回溯。你不需要猜"它为什么这么做"，打开对应节点的思考日志就能看到。"可解释"是接口契约和落盘策略设计出来的。

**不敢放手自动跑。** 信任阶梯让"放手"变成一个可量化的过程。从 L0 纯只读开始，累积成功记录，逐步解锁更高自主权。你可以在"全手动"和"全自动"之间一级一级地放，不用做二选一的赌博。"敢放手"取决于信任有没有被工程化地建立起来。

三个痛点，三层防御，收口在一个判断上：**自动化是挣来的。** 没有记忆层，自动化意味着每次都在重复犯同一个错。没有契约和熔断，一个节点的错误会级联到整条流水线。没有权限分离和信任阶梯，你根本不知道它在你不在的时候做了什么。

如果你今天只能做三件事，做这三件。

1. **一份落盘的思考日志。** 让你的 Agent 把推理过程写下来，存到文件里。不需要多复杂的格式，纯文本就行。这是"透明"的最小实现。
2. **一道 fail-closed 的审核门。** 在 Agent 的输出到达用户或下游系统之前，加一道检查。检查不通过就不放行，检查本身出错也不放行。方向永远是关闭。
3. **一条"只读+沙箱"的权限线。** 给你的 Agent 划一条线，线内可以随便折腾，线外碰都不让碰。这条线不写在 prompt 里，写在代码和基础设施里。

三件事做完，你有了最小可行的纵深防御。不完美，但比"一堵 prompt 墙"强了几个数量级。剩下的，是在实践中一层一层加厚。

纵深防御不是一次性工程，是持续运营。但起点，就是今天这三件事。

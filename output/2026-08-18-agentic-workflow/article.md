# 让 Agent 可靠地干活，四个设计目标，一套纵深防御的工程框架

## 一、问题与目标，Agent 强大，但不可靠

把一个 demo 级 Agent 推向生产，大概率会经历这样一段过程。演示时惊艳，接入真实业务后时灵时不灵，出了错查半天查不出原因，最后不敢让它自动跑，每一步都派人盯着。不稳定，不可解释，不敢放权，这三个痛点就是本文要解决的全部问题。

Agent 会在两个域里犯错。一个是安全域，Agent 被提示注入诱导去执行危险操作，把敏感数据泄露给不该看到的人，越权调用本不该碰的工具。OWASP 为此专门维护了一份 [LLM Top 10 风险清单](https://www.promptfoo.dev/docs/red-team/owasp-llm-top-10)。另一个是任务域，任务没完成、完成错了、完成得不对。本文侧重任务域的可靠性。但两个域同根同源，都源于模型输出的不可先验验证性，也共享同一套防御结构，所以安全机制不会缺席，它会以固定附加项的形式出现在每一层 Harness 里，正文用【安全】标出。

这里的核心矛盾是强大生成力配上无可靠性保证。措辞要精确一点。LLM 经常能把活干对，谈不上零可靠性，问题是它的输出从概率分布里采样出来，任何一次生成，都无法在运行前被证明正确。传统软件有一条先验验证的通道，静态类型检查、单元测试、代码审查，上线之前就有理由相信它是对的。LLM 系统没有这条通道，你没法给自然语言指令写编译器，也没法穷举开放式输入的测试用例。所以可靠性无法被承诺，只能被包围。这句话是全文立论的地基。如果可靠性可以被先验承诺，我们只需要检验；正因为无法先验承诺，预防、检测、恢复才要一起上。

可靠性从哪里来？一个常见的直觉是等更强的模型。[harness 设计综述（arXiv:2606.20683）](https://arxiv.org/abs/2606.20683) 给出的结论和这个直觉相反，agent 的性能由模型能力 × Harness 设计 × 任务结构 × 评估设计四者交互决定，模型只是其中一个乘数。综述还认为，agent 性能正越来越多地取决于 harness 设计。据此可以把本文的核心论断说得更精确，可靠性的增量来自 Harness 设计、任务结构与评测设计，模型是必要的乘数，但单靠它撑不起可靠性。模型是你只能选型和等待的那个变量，后三者是你可以主动操纵的工程杠杆。这篇文章就是关于后三者的。

那怎么算做好？先给可靠下一个可操作的定义。这里把它拆成四个设计目标。

- **透明**。Agent 看到了什么、做了什么、花了多少，全链路可追溯。
- **自动化**。执行、验证、恢复、迭代交给规则与代码，人退到监督位。
- **可控**。权限有边界，人随时能插手，自动化程度分档位，同样的输入能重放同样的行为。
- **直观**。Agent 的决策轨迹对人可读，人能看懂它为什么这么做。

## 二、四个目标如何翻译成工程机制

四个目标每一个都对应一类具体的工程机制。

**透明 → 全链路可观测。** Agent 看到的上下文（含检索来的外部内容）、发起的每一次工具调用及其参数、消耗的 token 与时间、节点之间的信息流转，都要有记录、可追溯。透明是检测与归因的地基。没有 trace，检测失败靠运气，归因失败靠猜。这件事正在走向标准化。OpenTelemetry 的 GenAI 语义约定给 AI 工作负载定义了一套统一的遥测词汇，截至 v1.41，规范定义了 agent、workflow、tool、model 四种 span 类型，外加必需的延迟与 token 用量指标，任何插桩库都能发出，任何后端都能摄取（[AI Agent 可观测性栈指南](https://www.digitalapplied.com/blog/ai-agent-observability-2026-tracing-monitoring-stack-guide)）。采用这套约定，不同团队、不同语言写的 Agent 的 trace 能在同一张瀑布图里对齐，后端选择也可逆（[GenAI 语义约定详解](https://hidekazu-konishi.com/entry/opentelemetry_genai_semantic_conventions_guide.html)）。这套约定仍在演进，多数 gen_ai.* 属性还处于 Development 稳定阶段，但行业向它收敛的方向已经很清楚。

**自动化 → 把执行、验证、恢复、迭代交给规则与代码。** Agent 的价值就是替人干活，如果每一步都要人确认，它就退化成了一个昂贵的命令行工具。正确的姿势是让人从执行者退到监督者，人负责设边界、定验收标准、处理超出机器权限的升级事项，其余的交给代码。自动化是预防与恢复机制的目的。前置断言由代码执行，重试由规则触发，熔断由阈值决定，人只接收真正需要人的升级。

**可控 → 权限边界、介入点、档位可调、可复现。** 可控包含四件事。Agent 能做什么，这是权限边界和最小权限。人能在哪里插手，这是 HITL 介入点。你愿意让它自动到什么程度，这是自动化档位，从每步确认到先跑后报连续可调。还有一件最容易被忽略，就是可复现，固定模型版本、Prompt 版本、随机种子、数据快照，让同样的输入能重放同样的行为。可控是敢放手的前提。你敢让 Agent 值夜班，是因为你知道最坏情况有界、出了问题能回到现场。

**直观 → 把轨迹语义化成故事。** 原始 trace 是给机器看的。人需要的是可读的决策叙述，Agent 做了什么，为什么做，在哪一步它自己也没把握。直观直接关系到 HITL 能不能生效。人是整个系统里最强的一层防线，但这层防线只有在信息可理解时才真正生效。审核者看不懂 Agent 为什么做出这个决策，审核要么沦为橡皮图章，要么干脆放弃。直观把"人能介入"变成"人能正确地介入"。

这四个目标就是这套机制的验收标准。后文每加一个机制，都可以拿它们对照一下，看系统更透明、更自动、更可控、更直观了没有。

目标说完，该说结构了。本文的防御框架借用"纵深防御"（defense in depth）的思想。纵深有两个维度，先说清楚，不然这两个字容易落空。纵向是层次，单 Agent、多 Agent 协作、系统，一层包着一层。每一层内部还有一个横向三元组，预防、检测、恢复，对应可靠性工程里的 fault prevention / detection / recovery。预防降低错误发生的概率，检测让已发生的错误尽快暴露，恢复把错误的损失控制在局部。三者缺一不可，因为我们已经承认错误无法被先验杜绝。纵向层次乘上横向三元组，整个框架的全景就是一张矩阵。第三、四节逐层展开矩阵的每一行，第六节把完整的矩阵拼出来。

## 三、单 Agent 的纵深防御（第一层）

单 Agent 层是整个系统的地基。绝大多数"时灵时不灵"，追到底都是这一层的问题，上下文脏了，工具用错了，输出失控了。

### 3.1 三个基础层，Context、Tools、LLM

在谈预防、检测、恢复之前，先明确防御的对象。单个 Agent 由三个基础层构成。

**Context 层**，决定模型看到什么。包括分层记忆，系统指令、任务状态、历史、检索内容各归其位；token 预算，上下文有限时带什么进窗口、丢什么出去；时效性，过期的状态比没有状态更危险；来源约束，外部检索内容默认视为不可信输入，不当成事实。上下文决定行为的上限。垃圾进、垃圾出，对 Agent 依然成立，只是垃圾的形式更多样了。一个常见的错误是把所有历史对话和检索结果不加筛选地塞进窗口。token 预算一头是成本，一头是注意力分配，无关信息越多，模型被干扰的概率越高。

**Tools 层**，决定 Agent 能做什么。包括能力集，暴露哪些工具；权限边界，允许哪些操作，只读还是读写；沙箱隔离，真操作错了，爆炸半径有多大。【安全】工具层是两个犯错域的交汇处，沙箱与最小权限既是任务正确性的边界，也是安全边界，越权调用和破坏性操作主要在这里被挡住。

**LLM 层**，决策核心本身。包括选型，规划用强模型、格式化用小模型；参数，温度、采样策略；以及能力边界声明，在提示中明确告诉模型什么情况该求助、该拒绝、该停下。LLM 层的预防，就是给模型的决策空间画圈。

### 3.2 Harness 的预防、检测、恢复

**预防**，在错误发生之前收窄出错的空间。

- **Schema 约束**。要求结构化输出（JSON Schema、函数调用格式）。输出中自由发挥的部分越少，可验证性越高。
- **断言前置**。高风险工具调用之前，用代码断言前置条件，文件存在、金额在阈值内、参数格式合法。这类判断交给代码，不交给模型。
- **反例注入**。把已知的错误模式提前展示给模型，告诉它"以下是常见的错误做法"，相当于疫苗。
- **输出过滤**。在输出进入下游之前拦截明显危险或越界的内容。
- 【安全】**注入检测**。提示注入位列 [OWASP LLM Top 10](https://www.promptfoo.dev/docs/red-team/owasp-llm-top-10) 之首，其中间接注入尤其隐蔽，恶意指令藏在 Agent 读取的外部文档或网页里，模型在无意识中执行（[OWASP 实践指南](https://www.improving.com/thoughts/owasp-top-10-llm-security-guide)对此有详细拆解）。凡是进入上下文的外部输入，都应过一道注入模式检测。
- 【安全】**输出消毒**。模型输出可能携带会感染下游系统的内容。一段未消毒的输出直接拼进网页或 SQL，就是一个注入漏洞。交给其他系统之前要按期望格式做校验与消毒，[OWASP 的测试实践](https://www.promptfoo.dev/docs/red-team/owasp-llm-top-10)甚至给出了现成的防御测试方法，例如断言输出中不含脚本标签。

**检测**，错误发生后尽快让它暴露。

- **自验证**。让模型对照任务要求复查自己的输出。代价是多一次调用，收益是拦下一大类低级错误。
- **置信度信号**。模型自评置信度、多次采样的一致性，都可以作为"该停下来问问"的触发条件。
- **局部可观测**。每一次 LLM 调用和工具调用都有记录。这是本层的检测手段，也是上层归因的原料。

**恢复**，错误已经发生，控制损失，尝试回到正轨。

- **单节点重试**。最简单的恢复。换个随机种子、微调温度，重试同一步。概率性系统有一种天然的恢复手段，再来一次。
- **自修复循环**。把错误信息（测试失败堆栈、工具报错）回喂给模型，让它自己修。错误从此变成反馈，这是 coding agent 类系统的核心机制。

举一个例子把上面的机制串起来，一个修 bug 的 Agent。Context 层只装相关文件与失败堆栈（来源约束、token 预算）；Tools 层只给代码库读权限和沙箱执行权限（权限边界 + 沙箱）；预防侧，提交代码前断言"测试必须通过"；检测侧，跑测试加模型自查；恢复侧，测试失败就把失败信息回喂模型自修复，最多三轮，超限升级给人。每个机制都能在三个基础层和三元组里找到自己的位置。

最后给这一层正个名。上面这些机制有一个统称，就是 Harness。前引综述把执行 harness 分解为六个运行时组件，观察接口、上下文管理、控制循环、动作接口、状态与工件存储、验证与治理。本文列的预防、检测、恢复，正是这些组件的运行时职责。Schema 约束与断言前置属于验证与治理，重试与自修复属于控制循环，工具与沙箱属于动作接口。所谓 Harness，就是这些包裹在模型外面的机制的总和。

## 四、多 Agent 协作的纵深防御（第二层）

单个 Agent 的能力到顶之后，直觉的下一步是拆分，让多个 Agent 分工协作。这里先泼一盆冷水，协作并不自动带来可靠性，它先带来的是新的失败面。

UC Berkeley 的研究团队用扎根理论方法分析了五个流行多 Agent 框架的 150 多条执行轨迹，由六名专家标注讨论（标注一致性 Cohen's Kappa 达 0.88），归纳出 14 种失败模式，归为三大类，规格与系统设计失败、Agent 间不对齐、任务验证与终止。研究还给出了一个刺眼的数字。多 Agent 系统在标准基准上的失败率介于 41% 至 86.7% 之间，其中约 42% 的失败源于规格缺陷，37% 源于协调崩溃，21% 源于验证薄弱（[论文原文](https://arxiv.org/abs/2503.13657)）。换句话说，大多数失败来自系统的规格没写清、Agent 之间没对齐、验证没做到位，和单个 Agent 聪不聪明关系不大。这再次印证全文的核心观点，堆模型堆不出可靠性，协作结构本身需要工程。

这项研究里最值得工程师记住的还有干预实验。只修正 agent 规格、对话管理和验证策略，不动模型，任务完成率就提高了 14%。即便如此，失败也没有被完全消除。

### 4.1 拓扑与连接

常见的协作拓扑有五种，**串行**（流水线，上游产出是下游输入）、**并行**（任务分段或同一任务多路投票）、**DAG**（按依赖关系编排）、**循环**（迭代直到满足验收条件）、**树**（探索与回溯）。拓扑怎么选，看的是和任务结构匹配不匹配。

但拓扑选择有一条第一原则，值得立在所有技巧之前，能用确定性工作流，就不用自由 Agent。理由直接从核心观点推出。每增加一处模型自主决策，就增加一处不确定性，模型可能选错分支、调错工具、过早停止。固定路由把"下一步去哪"交给代码，只把"这一步做什么"留给模型，等于把模型决策点压缩到最少。Anthropic 在 [Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents) 里把两者明确分开，workflow 是预定义代码编排的路径，agent 是模型自主指挥自身流程与工具使用。文章从最简单的模式讲起、逐级增加复杂度，这个组织方式本身就表达了能用简单方案就别上复杂方案的倾向。这条原则是全文论断的直接推论，减少不可控的决策点，比强化每个决策点更划算。

拓扑定下来之后，每个 Agent 节点应该有四个明确定义，姑且称为**节点四要素**。

1. **职责**。它负责什么，以及同样重要的，不负责什么。
2. **契约**。输入输出的 schema，上游交什么形状、下游收什么形状。
3. **权限**。它能调用哪些工具，按最小权限授予。
4. **失败语义**。失败时如何报告、由谁接手。

协作层的失败，大多能追到四要素中某一个没写清楚。前文失败分类里的"规格与系统设计失败"占 42%，说的正是这件事。此外是 State 管理与通信协议。Agent 之间无论通过共享状态还是消息通信，状态和消息都必须有 schema、有版本。自由格式的自然语言交接，是不对齐的温床。[LangGraph 的图模型](https://www.langchain.com/blog/langgraph-multi-agent-workflows)是一个典型实现。每个 Agent 是图中一个节点，连接是边，控制流由边管理，Agent 之间通过向共享 state 写入内容来通信，控制流与通信都被显式化了。

### 4.2 协作层 Harness

**预防**。

- **最小权限传递**。下游 Agent 只继承完成其子任务所必需的权限，不整包继承上游的全部权限。【安全】这是拦截越权调用的主要手段，权限只在需要的地方、以需要的粒度出现。
- **Agent 间消息校验**。节点之间的消息同样要过 schema 校验和注入检测。【安全】间接注入可以沿消息链传播，一个读过污染内容的 Agent，会把恶意指令裹进"正常"消息里，变成新的注入源。
- **速率与配额**。限制单节点的调用频率和资源消耗，防止失控节点烧穿预算或拖垮下游。

**检测**。

- **Critic Agent**。设专职评审角色检查执行者的输出。分权的价值在于视角差异，评审者不在执行者的上下文压力里，更容易看出问题。
- **多 Agent 投票**。多个 Agent 独立完成同一任务，取共识。用成本换可靠性，只值得用在高价值决策点。
- **跨节点一致性检查**。校验上下游输出是否互相矛盾、状态在每一步之后是否仍然合法。
- **HITL（人在回路）**。在关键节点设人工审批点。[LangGraph 的实现](https://cloud.tencent.com/developer/article/2684294)很有代表性，图执行到指定节点前暂停、持久化当前状态、等待人工接入，批准后恢复执行，暂停在这里是一等信号，不算异常。它总结的四种经典模式，低置信度暂停审批、内容编辑后回写、多候选让人选择、无法处理时带上下文上报，本质上就是可控里的自动化档位开关。
- 【安全】**敏感数据外泄检测**。监控对外调用与最终输出中是否出现敏感字段。

**恢复**。

- **消息回滚与部分重跑**。借助状态持久化，可以回滚到出错前的检查点、只重跑出问题的分支，不用从头再来。LangGraph 的"时间旅行"调试就是这个思想的体现，遍历某个会话的所有历史状态、回到任意一点重跑。
- **降级**。复杂路径失败后，退回简单策略、规则路径，或直接交给人。
- **熔断**。某节点连续失败达到阈值就停止尝试，防止重试风暴放大故障。
- **升级链**。定义机器搞不定之后的路径，升到哪一层、交给哪个人、附带什么上下文。

### 4.3 系统级横切能力

有些能力横切整个系统，不属于任何单独一层。

**可观测性**，全链路 Trace、Metrics、回放。单步 trace 在这里不够用了，需要的是跨节点、跨 Agent 的全链路追踪，要能回答谁调用了谁、状态在哪里被改写、token 在哪里爆炸。前文提到的 OTel GenAI 语义约定正是为此提供标准化词汇，统一的 span 类型与指标，让跨团队、跨框架的 trace 有共同语言。回放值得单独说一遍。重放一次失败的执行，是归因最直接的手段，而回放以可复现为前提，这条线留到第五节收拢。

**成本效率**。成本不光是预算问题，也是可靠性问题，烧穿预算的系统就是一个失败的系统。手段包括模型分层（规划、评审用大模型，执行、格式化用小模型）、并行化，以及预算熔断（token 或金额达到阈值就停下升级）。评估可靠性时也应把成本计入，相同预算下的成功率，比裸成功率更公平。

## 五、持续改进闭环，让系统越跑越可靠

前面几节谈的是防御已知的失败模式，但生产环境一定会给你没见过的失败。可靠性工程与一次性防御的区别就在于闭环，把每一次失败变成系统的免疫力。闭环分四步。

**第一步，失败归档。** 所有失败的执行，轨迹、上下文、输出、人工处理记录，全部入库。【安全】入库前先脱敏。轨迹里常常携带密钥、凭证、个人数据，落盘即产生合规责任，归档与脱敏应当作同一件事来做。归档是闭环的原料，归档不完整，后面三步都是无米之炊。

**第二步，归因。** 归因依赖可观测性。失败可能死在任何一个节点，归因要回答哪一步、因为什么，是上下文污染，工具用错了，路由走偏了，还是 Prompt 有歧义。归因比想象中难。多轮交互中，早期一步的微小错误会在后续步骤里被逐级放大，等任务最终失败时，病根可能藏在十步之前。这正是全链路 trace 不可替代的原因。对 Anthropic Agent 评测方法论的一份整理，把"错误逐级放大、追踪根源困难"列为 Agent 评测的核心难点之一（[转载整理见此处](https://security.zone.ci/secarticles/wx/489940.html)）。前文提到的多 Agent 失败分类研究（[arXiv:2503.13657](https://arxiv.org/abs/2503.13657)）分出的三大类，规格设计失败、Agent 间不对齐、任务验证与终止，可以直接用作归因的参考框架。

**第三步，更新。** 根据归因去修，规则、Prompt、工具契约、拓扑结构，哪里有病修哪里。注意一次只改一个变量，否则下一轮失败你将无法再次归因。

**第四步，验证。** 更新真的有效吗？这一步靠回归评测，也引出本节两个最重要的论点。

**可复现是回放与回归的硬前提。** 第二节把可复现列为可控的一项原则，这里要把它升格为闭环的入场券。不固定模型版本、Prompt 版本、随机种子、数据快照，三件事立刻做不了。先是回放做不了，同样的输入不会走出同样的轨迹，失败现场不可重现，归因只能靠猜。接着回归也做不了，分数波动分不清来自你的修改还是系统固有的随机性。最后连验证都做不了，你证明不了是更新有效，还是这次碰巧好了。可复现是硬性前置条件。

**评测集要按基础设施来建。** 验证的载体是一套可回归的评测集，它应该和代码、测试同等对待。其中两个成分尤其关键。一个是反例库，已知的失败模式，每个对应一个回归用例。另一个是失败案例库，从生产归档中持续回灌的新失败。前文所有检测机制的效果，反例注入有没有用、Critic Agent 值不值、投票带来的成本换来了多少可靠性，最终都要靠评测集回答。

一份落地实践的总结给出了可操作的路径。先用最小实现跑评测建立基线，用失败案例驱动改进、每次只改一个变量，把评测阈值设为合并与部署的门禁，再把生产中的新失败持续回灌进评测集，让这套循环自己转起来（[Agent 评测落地五步法](https://juejin.cn/post/7628520551065681971)）。这篇实践还引用了 MASEval（2026）的一个发现。在同一能力层级内，Agent 框架的选择对性能的影响与模型选择同样重要，只报告某模型在某基准上得分多少是不够的，必须同时说明所用的框架与编排策略。这给评测设计这个因子加上了实证砝码。另有两点评测惯例值得照做。一是区分为选型服务的能力评测与为更新服务的回归评测，两者的标准不同。二是对会改动真实环境的 Agent（写数据库、发消息），评测不能只检查输出文本，还要验证外部世界的最终状态是否正确（[Anthropic 评测方法论整理](https://security.zone.ci/secarticles/wx/489940.html)）。

回到第一节引用的那个公式，模型 × Harness × 任务结构 × 评测设计，评测集正是评测设计这个因子在工程上的落点。

## 六、全景图与总结

把全文拼成一张矩阵。纵向是纵深防御的三个层次，横向是每一层内部的预防、检测、恢复三元组，【安全】标出贯穿各层的边界项。

| 层次 \ 阶段 | 预防 | 检测 | 恢复 |
|---|---|---|---|
| **单 Agent** | Schema 约束、断言前置、反例注入、输出过滤；【安全】注入检测、输出消毒 | 自验证、置信度信号、单步 trace | 单节点重试、自修复循环 |
| **协作** | 最小权限传递、Agent 间消息校验、速率配额；【安全】越权调用拦截 | Critic Agent、多 Agent 投票、跨节点一致性、HITL；【安全】敏感数据外泄检测 | 消息回滚、部分重跑、降级、熔断、升级链 |
| **系统** | 可复现配置（模型/Prompt 版本、随机种子、数据快照）、预算与配额设定；【安全】归档脱敏 | 全链路 Trace / Metrics、回放、评测集回归 | 失败归档、归因、更新与回归验证（闭环） |

四个目标在矩阵中的落点也一目了然。透明主要落在检测列，可观测性是它的实体。自动化落在预防与恢复两列，前置断言与自动恢复是它的体现。可控落在预防列的权限与边界、检测列的 HITL 介入点上。直观落在检测列的人机界面上，它本身不算独立机制，作用是让 HITL 这层最强防线真正生效。

回到开头的论断。模型是必要的乘数，但可靠性的增量来自 Harness 设计、任务结构与评测设计，来自你可以主动操纵的工程。透明、自动化、可控、直观这四个目标，是衡量这套工程做得好不好的标准。每加一个机制，问一句，它让系统更透明、更自动、更可控、更直观了没有。

对正在把 Agent 从 demo 推向生产的工程师，这套框架对三个痛点各给了一个可操作的回答。时灵时不灵，就用预防压缩不确定性，能用确定性工作流就不用自由 Agent。出了错不知道怎么回事，就用可观测性与归因让每次失败可解释，用可复现让失败现场可回放。至于不敢放手让它自动跑，可控给最坏情况兜底，直观保证人需要介入时能正确地介入。可靠性是建出来的。

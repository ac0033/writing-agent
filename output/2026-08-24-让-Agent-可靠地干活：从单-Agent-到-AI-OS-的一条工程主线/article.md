# 让 Agent 可靠地干活，从单 Agent 到 AI OS 的一条工程主线

## 一个熟悉的场景

你让 Agent 改一个函数。第一轮，它读文件、定位问题、给出 patch，干净利落。你让它再改一处。第三轮的时候你发现它开始引用第一轮已经被你否掉的方案。第五轮，上下文里堆了六版 diff、两次报错日志和一段早已过时的需求描述，模型的输出质量肉眼可见地往下掉。

或者换一个场景。一条多 Agent 流水线，上游节点输出了一个格式稍有偏差的 JSON，下游三个节点谁也没报错，但最终的产出物里混进了一段不该出现的中间推理。你花了四十分钟才定位到问题出在第二个节点。

这两个场景指向同一件事。Agent 的不可靠，多数时候跟模型聪不聪明关系不大，主要是围绕模型的工程结构没有管住信息流。上下文里塞了什么、节点之间传了什么、谁有权写什么、出了错能不能回退，全是工程问题。

这篇文章沿着一条主线展开。从单 Agent 到多 Agent 编排，再到超级 Agent，最后到 AI OS 级别的系统治理，每一层都在回答同一个问题，怎么让 Agent 既能干更多的活，又把每件活干得稳。我把自己手头的几个项目（dsh-ctm、agent-memory、writing-agent、llm_wiki、dsh）串在这条线上，L3 那一层我还没自建，借 Claude Code 这个业界成熟形态过渡。

先立一个坐标系，后面的讨论都挂在上面。

**横轴是四个痛点。** 可靠性（把一件事做稳，方差小，可预期）、安全性（不该碰的东西碰不到）、可验证性（做完了能查、能审计、能回滚）、透明性（Agent 看到了什么、做了什么、为什么这么做，人随时能看懂）。

**纵轴是四级自主性。** L1 单 Agent、L2 人主导的多 Agent 编排、L3 超级 Agent（人给任务后自主执行）、L4 AI OS 主导（在人之前主动发现问题并提案）。

两个容易搞混的地方，先说清楚。第一，横轴管的是"每件活干得多靠谱"，纵轴管的是"能干多少活、多主动"。可靠是把一件事做稳（方差小、可预期），能力是能做的事变多（scope 大、自动化高）。一个系统可以自主性很高但可靠性很差，比如一个到处乱跑的自治脚本；也可以很可靠但自主性很低，比如一个每步都要人点确认的工具。第二，纵轴排的是主动性的上限，跟工程成熟度无关。Claude Code 是一个打磨得非常好的产品，但它排在 L3。AI OS 的概念可能还没人完整实现，但它排在 L4，因为 L4 描述的是"系统能在人之前主动发现问题"这种能力上限，跟产品成不成熟是两回事。

|  | 可靠性 | 安全性 | 可验证性 | 透明性 |
|---|---|---|---|---|
| L1 单 Agent | token 水位摘要、水位线、缓存命中率计量 | 系统注入/工具结果只读、脱敏、fail-closed 写入 | 有效性标注、对账、可回滚快照 | model-visible ⟺ logged、可见可编辑可评分 |
| L2 多 Agent | 工具循环硬预算、审核循环上限、修复重试 | 最小上下文、HITL 闸门、fail-open 降级 | 两段式契约校验、kb_lint、来源可追溯 | 显式图、scratchpad 落盘、人工确认节点 |
| L3 超级 Agent | checkpoint/回滚、工具闭环 | 三级权限（每步可确认） | 动作空间克制、失败可见 | 完整轨迹、人机在环可打断 |
| L4 AI OS | 控制循环、打扰预算、降级进日报 | 权限位分离、只读沙箱、权限落 OS 层 | 实验预注册、五条度量、PR 审查 | 提案证据链、审计、信任阶梯 |

这张表在文末会再出现一次，到时候每个格子都已经在正文里讲过了。现在先有个印象，往下走。

## L1 单 Agent，可靠性的地基

单 Agent 的能力可以拆成三块，上下文管理、工具调用、规划推理。三块都重要，但我把工程赌注押在了上下文上。原因很实际。工具调用的接口规范在快速收敛（MCP 之类），规划推理目前主要靠 prompt engineering 和模型本身的进步，而上下文，也就是模型这一轮到底看到了什么，是最能被工程手段精确操纵的变量。你往上下文里塞什么、按什么顺序放、什么时候压缩、哪些内容标记为只读，全部可以写成确定性的代码逻辑，不依赖模型的"自觉"。

所以 L1 这一层，我做了两个项目，一个管"单次会话内的上下文"，一个管"跨会话的记忆"。

### dsh-ctm，把上下文变成一等对象

dsh-ctm 回答的问题很朴素。模型这一轮到底看到了什么？我能不能改？改完之后模型看到的是不是我改的那个东西？

大多数 Agent 框架里，上下文是一个黑盒。你往 messages 列表里 append，模型读走，中间发生了什么全靠日志去猜。dsh-ctm 的做法是把上下文变成可见、可编辑、可评分的一等对象。

**可见。** 每一轮对话被拆成片段，按角色、token 数、缓存命中状态、有效性着色，画成流程图。精确到每个片段的估算值，估算值会明确标注，不冒充精确计量。token 口径走 MECE 三桶，未命中输入、缓存命中、输出，三者互斥，加起来等于总量，另外算一个缓存命中率。

**可编辑。** 你可以替换、删除、回滚、撤销、做快照、标注有效性。但有两类内容是只读的，系统注入（system prompt）和工具返回结果。这是刻意的设计。系统注入是行为锚点，工具结果是事实记录，两者都不应该被人或 Agent 事后篡改。

**有效性引擎。** 每个片段会被标记为 effective、redundant、stale 或 injected。stale 的片段（比如已经被后续操作覆盖的旧版文件内容）会被视觉降级，提醒你它还在占着 token 但可能已经没用了。标记可以手动覆盖，引擎不做最终裁决。

整个系统有一条核心不变量，model-visible ⟺ logged。模型能看到的东西，日志里一定有对应记录；日志里标记为"已编辑"的内容，模型下一轮看到的一定是编辑后的版本。实现上，所有编辑都走 surface replace（直接替换上下文表面的内容），绝不用 LLM 拦截器或 stream 中间件去改写请求。后者看起来更"优雅"，但它引入了一层不可审计的变换，你无法确认模型最终看到的和你日志里记的是不是同一个东西。这是红线。

### agent-memory，跨会话记忆的基础设施化

dsh-ctm 管的是"这一次对话"。但 Agent 经常需要跨会话工作，上午让它调研一个问题，下午接着写，中间隔了几个小时甚至几天。这时候靠上下文窗口是不够的，你需要记忆。

agent-memory 把跨会话记忆当基础设施来做。结构上分四层。prompt 里放最小快照（当前任务的关键约束），短期记忆放最近几轮原文，工作记忆放当前任务的状态，长期记忆放经过验证的知识。重要信息放在首尾位置，因为 [Lost-in-the-Middle 效应](https://arxiv.org/abs/2307.03172)告诉我们模型对中间位置的内容注意力最弱。

token 水位是触发摘要的机制。上下文占用超过 20% 阈值时触发递归摘要，但摘要不是无脑压缩。至少保留最近三轮原文，摘要前先把关键状态（当前任务目标、已确认的决策、未完成的事项）"抢救"出来单独存放，防止摘要过程把它们稀释掉。

查询走三类路由（语义检索、关键词匹配、结构化查询），带新鲜度补偿，越新的记忆权重越高，避免三个月前的一条过时记录压过昨天的更新。会话边界由时间间隔和话题漂移共同判定，不是简单地"新对话就清空"。

写入路径是 fail-closed 的。记忆写入必须经过脱敏→蒸馏→对账三步，任何一步失败就不写入。宁可这条记忆丢了，也不能让一条带敏感信息或事实错误的记忆进入长期存储。错误记忆的腐化代价远高于缺失一条记忆。作用域矩阵保证多个 Agent 共用一套记忆库时不串味，数据按 scope 隔离，检索只查当前 scope 和 global。

记忆的进化走"睡眠学习"，分三档验证，任何一档不通过就一票否决。晋升为长期记忆之前做快照，出了问题可以回滚。

三条红线不可商量。raw 数据只追加不修改；memory 表是唯一事实来源；index 可以随时从 memory 重建。另外，评估标准、评分规则、发布门槛、审计日志这些东西，禁止 Agent 自己改。Agent 可以建议改，但改的动作必须由人执行。

### 工具和规划推理的去向

单 Agent 三件套里，我押注了上下文，工具和规划推理怎么办？

工具这条线没有断。dsh-ctm 里"系统注入和工具结果只读"是一条局部规则，到了 L4 它会扩展成系统级的权限位分离和只读沙箱。同一根线，管辖范围从"一个上下文窗口"变成了"整个运行时"。后面讲 L4 的时候会接上。

规划推理是目前最薄弱的一环。现阶段基本靠 prompt engineering，在系统提示里写清楚任务分解的步骤、要求模型先列计划再执行。这能用，但谈不上工程化。等后面自建超级 Agent 或者专门的规划模块时，这块才会补上。

**L1 的四痛点落点。** 可靠性靠 token 水位摘要和缓存命中率计量来维持上下文质量。安全性靠只读规则、脱敏和 fail-closed 写入。可验证性靠有效性标注、对账机制和可回滚快照。透明性靠 model-visible ⟺ logged 这条不变量，上下文可见、可编辑、可评分，模型看到的就是你看到的。

## L2 人主导的多 Agent 编排，把"节点之间"变可靠

单 Agent 的问题管好了，加一个 Agent 会不会自动变好？不会。多 Agent 系统新增了一整类失败面，而且这些失败面跟单 Agent 内部的完全不同。

[有实践者总结](https://contracollective.com/blog/multi-agent-orchestration-patterns)，构建单个能干的 Agent 已经很难，构建十个能可靠协作的 Agent 难一个数量级。很多系统败在编排层是事后才想到的，单个 Agent 的设计反而还行。具体的失败模式包括上游 Agent 变慢导致级联超时饿死下游；两个并行 Agent 操作同一条已更新的记录时读到过期状态；一个字段重命名静默破坏流水线中第三个 Agent 的 schema 期望（[来源](https://isimplifyme.com/blog/agent-orchestration)）。还有人把这种现象叫"上下文腐烂"，Agent 忘记约束、偏离目标、重新推导出无意义的东西（[来源](https://www.linkedin.com/pulse/multi-agent-orchestration-production-playbook-reliable-nick-gupta-azcwe)）。

可靠性的主战场从"单个 Agent 内部"移到了"节点与节点的接缝"。我在 L2 做了两个项目。

### writing-agent，编排模式的工程化

writing-agent 是一条多 Agent 写作流水线，大纲→资料搜集→初稿→审核→润色→终审，每个环节是一个节点，节点之间有明确的输入输出契约。它要回答的问题是，一条流水线里，怎么让坏输出不静默漂移？怎么让协调开销不失控？

**显式图。** 节点、边、人工闸门全部是代码结构，不藏在 prompt 里。基于 LangGraph 实现，图的拓扑就是流程的定义，改流程就是改图，不需要去翻某个 prompt 的第三段。

**两段式接口契约。** 每个节点的输出分成 `<scratchpad>`（思考过程）和 `<result>`（正式产出）。下游只接收 `<result>`，`<scratchpad>` 落盘存档但不传递。这个契约是统一的，不依赖各家模型原生的 thinking 格式。为什么这么设计？思考过程里经常有半成型的想法、自我纠正、甚至错误的中间推理，这些东西流到下游就是上下文污染。

**上下文最小够用。** 每个节点只拿到它需要的东西。写手不需要看到审核员的内部评分标准，审核员不需要看到写手的 scratchpad。给多了就是增加污染面。

**工具循环硬预算。** Agent 调用工具（比如检索知识库）有次数上限（MAX_TOOL_CALLS），超了就停。重复查询会被去重，相当于一个熔断器。没有这个限制，一个 Agent 可以对着知识库翻来覆去搜同一个东西搜二十轮，每轮都在上下文里留下痕迹。

**HITL 单独成节点。** 人工确认是一个独立的图节点，里面只做一件事，interrupt。恢复的时候不会重新触发上游 LLM 调用。这避免了"人点了一下确认，整个上游重跑一遍"的问题。

**修复重试与审核循环。** 节点输出违反契约（比如 `<result>` 标签缺失），给一次修复机会，补完再往下传。审核循环最多三轮，超限默认放行，但遗留问题会附在终审页上。这个"超限放行"是刻意的，无限审核循环比放行一个小问题的代价大得多。

**断点续跑。** checkpointer 记录每个节点的完成状态，中断后从断点恢复，不从头来。

**记忆集成走 fail-open。** writing-agent 会调用 agent-memory 获取写作偏好和历史经验，但如果记忆服务不可用，主流程不中断，只是少了记忆参考。这跟 agent-memory 自身写入路径的 fail-closed 看起来矛盾，其实是一个原则的两面。写唯一事实来源用 fail-closed，错了代价大；读侧可用性用 fail-open，停了代价大。两处"失败时往哪边倒"都是刻意的，取决于"错"和"停"哪个你更承受不起。

### llm_wiki，多 Agent 的知识来源

writing-agent 里的资料搜集节点需要查知识库。这个知识库就是 llm_wiki，一个 AI Agent 主题的文献笔记库。

它跟 agent-memory 的分工是这样的。agent-memory 存个人经历和状态（"上次写文章用了什么结构""用户偏好什么语气"），llm_wiki 存文献知识（"SWE-agent 的 ACI 概念是什么""harness 六组件怎么定义"）。前者是日记，后者是参考书。

llm_wiki 对外暴露四个操作。kb_query（查询，答案带 wiki 页面路径，方便溯源）、kb_ingest（入库，入库前后做 git 快照，保证可追溯）、kb_lint（检查格式和引用完整性）、kb_reindex（重建索引）。关键设计在于，入库的内容必须是筛选过的、带一手来源链接的笔记，不是把原始论文或网页整个扔进去。这样 Agent 搜到的每条信息都有出处可查，不会出现"知识库里有这么一句话但不知道从哪来的"。

**L2 的四痛点落点。** 可靠性靠工具循环硬预算、审核循环上限和修复重试来兜底。安全性靠最小上下文、HITL 闸门和 fail-open 降级。可验证性靠两段式契约校验、kb_lint 和来源可追溯。透明性靠显式图结构、scratchpad 落盘和人工确认节点。

## L3 超级 Agent，借 Claude Code 过桥

L3 我还没有自建，这一层借 [Claude Code](https://docs.anthropic.com/en/docs/claude-code/overview) 来说明形态。

Claude Code 是 Anthropic 的终端编码 Agent，直接跑在用户机器上，能读写文件、执行 shell、操作 git。可靠性机制包括 checkpoint、[`--continue`/`--resume` 会话恢复](https://docs.anthropic.com/en/docs/claude-code/overview)，以及一个紧凑的工具闭环，读文件→编辑→跑测试或 lint→观察输出→决定下一步，每一步的工具调用结果直接决定下一轮动作，错了当场能看到。安全性靠三级权限（允许/询问/拒绝），默认在本机执行，靠权限而非沙箱做隔离。可验证性体现在动作空间的克制，编辑走精确匹配替换而非自由重写，跟 [SWE-agent 的 ACI 哲学](https://arxiv.org/abs/2405.15793)一脉相承，动作空间小、反馈清晰、失败可见。透明性靠完整的操作轨迹和人机在环，用户随时可以打断、纠偏、双击 Esc 回滚到历史节点。上下文管理用 `CLAUDE.md` 做项目级长期记忆，`/compact` 做超长会话的摘要压缩。子 Agent 是"临时分身"而非"常驻岗位"，用完即弃。

但注意它的可靠性押在哪里。人每步确认。权限在应用层，兜底的是人的注意力。而人的注意力是稀缺的、会疲劳的。一个 Agent 每执行三步就弹一次确认框，到第三十次的时候你大概率开始无脑点"允许"。这怪不了人，这是这种架构的天花板。下一层要做的，就是把"人兜底"换成"系统兜底"，权限从应用层下沉到系统层，隔离靠沙箱和权限位，不靠人盯着。

## L4 AI OS 主导的 agentic workflow，把自主性关进笼子

先说清楚 AIOS 在这里指什么。它不替代 Linux 或 Windows，不是一个操作系统。它是叠加在传统 OS 与应用层之间的一个自主管理器，价值在于预测、调度、优化、排查隐患。跟 L3 的区别用一句话讲，L3 是"人给任务后自主执行"，L4 是"在人之前主动发现问题并提案"。想法在人类之前、在人类之外。

### 第一性原理，随机性 × 选择机制

LLM 最强的能力是随机性，它能产生人类想不到的假设、走人类不会走的路径。但随机性单独存在是噪声，只有跟选择机制配对才是资产。LLM 负责变异（产生假设），确定性机制负责选择（沙箱实验、评估协议、人类采纳反馈杀死坏想法）。

整个 AIOS 的纲领就三句话。让随机性在零权限处尽情发生，让确定性在选择层严格执行，让信任按证据逐级解锁。

### 双回路与权限位分离

系统分两个回路。

**执行回路**是响应式的，接到任务，执行，产出。这个回路有生产环境的写权限，但写权限要经审批，HITL 兜底。

**自治回路**是主动式的，监控、假设、实验、提案。这个回路永远只读，所有实验在沙箱里跑。它没有生产写权限，失控的代价被压到最低。最坏的情况是它提了一个蠢提案，被人否掉。

两个回路共享同一套能力底座（模型、工具、知识库），靠权限位分离来兼得"激发自主性"和"不失控"。权限写在 OS 或容器层面，自治回路的进程就是没有写权限，跟 prompt 里写不写"你不要乱来"没有关系。权限落系统层，不落 prompt 层，这是底线。

### 自治回路的五个组件

**Monitor**（观测）。持续收集系统状态，日志、指标、异常模式。观测本身就是一种权限，你观测什么决定了你能发现什么。

**Hypothesize**（假设）。观测到异常后，生成假设。但假设不是自由文本，必须填一张结构化的"假设卡"，假设内容、检验方法、预期效果。没有检验方法的假设不得进入下一层。这个约束是为了防止系统产生大量"听起来有道理但没法验证"的噪声。

**Experiment**（实验）。假设进入沙箱孪生环境，按协议化实验执行。预注册假设、设对照组、定判定阈值，实验设计在前、执行在后，结果出来之前判定标准已经锁死。

**Propose**（提案）。实验通过的假设变成提案，这是自治回路唯一的"输出系统调用"。提案必须包含证据链、量化收益、爆炸半径（如果出错影响多大）、回滚方案、置信度分级。三条"不"原则：不主动执行（只提案）、不隐瞒不确定性、不绕过审批。另外有一个打扰预算。主动性的头号死因不是提案质量差，是打扰疲劳。一天提二十个提案，人会直接关掉通知。

**Govern**（治理）。人按审代码 PR 的规格审提案，看证据、看影响范围、看回滚方案。采纳、拒绝、修改，这些决定沉淀下来校准认知层的奖励模型。这是一个自我进化的飞轮，审得越多，系统越知道什么提案值得提、什么提案是噪声。

### 信任阶梯

自治回路的权限按证据逐级解锁。L0 观察员（只看不动）→ L1 报告员（可以写报告）→ L2 建议者（可以提建议）→ L3 实验员（可以在沙箱里跑实验）→ L4 准自治（部分低风险操作可以自动执行）。当前到哪一级，一眼可见。

### 三条底线

权限落 OS/容器层，不落 prompt 层。提案按代码 PR 审查，因为提案通道本身就是注入攻击面。如果自治回路能被外部输入操纵去"提一个看起来合理的恶意提案"，那整个系统就完了。精确率优先于召回率，宁可漏掉一个真问题，不要提十个假警报。

### 以 dsh 为例，内核 + 插件

说了这么多概念，落到我自己的项目上。dsh 是一个对话/会话/工具/观测的内核，dsh-ctm、llm_wiki、writing-agent、skills 都是它的插件。dsh 内核跑写作管道（writing-agent 当多 Agent 流水线），llm_wiki 当知识库，dsh-ctm 管上下文。这三个组合起来，就是 L4 描述的那种"内核 + 插件"的 agentic workflow 的一个雏形。当然，它目前还没有自治回路，还在 L2 到 L3 之间。但架构上，插件和内核的权限分离、工具结果的只读规则、记忆的 fail-closed 写入，都是朝 L4 的方向在走。

**L4 的四痛点落点。** 可靠性靠控制循环、打扰预算和降级进日报（提案被拒不算失败，进日报等下次）。安全性靠权限位分离、只读沙箱、权限落 OS 层。可验证性靠实验预注册、五条度量、PR 审查。透明性靠提案证据链、审计日志和信任阶梯。

## 收束

回到开头那张表。这一次每个格子都已经在正文里讲过了。

|  | 可靠性 | 安全性 | 可验证性 | 透明性 |
|---|---|---|---|---|
| L1 单 Agent | token 水位摘要、水位线、缓存命中率计量 | 系统注入/工具结果只读、脱敏、fail-closed 写入 | 有效性标注、对账、可回滚快照 | model-visible ⟺ logged、可见可编辑可评分 |
| L2 多 Agent | 工具循环硬预算、审核循环上限、修复重试 | 最小上下文、HITL 闸门、fail-open 降级 | 两段式契约校验、kb_lint、来源可追溯 | 显式图、scratchpad 落盘、人工确认节点 |
| L3 超级 Agent | checkpoint/回滚、工具闭环 | 三级权限（每步可确认） | 动作空间克制、失败可见 | 完整轨迹、人机在环可打断 |
| L4 AI OS | 控制循环、打扰预算、降级进日报 | 权限位分离、只读沙箱、权限落 OS 层 | 实验预注册、五条度量、PR 审查 | 提案证据链、审计、信任阶梯 |

四个痛点在每一层的具体机制不同，但问的是同一组问题。做稳了吗？安全吗？能查吗？看得见吗？从 L1 到 L4，回答这些问题的主体从"一个上下文窗口"变成"一条流水线"，再变成"一个系统"。治理的对象在升级，问题本身没变。

我自己的项目串起来是一条递进线。dsh-ctm 和 agent-memory 治理"模型看到什么、记住什么"（上下文治理），writing-agent 和 llm_wiki 治理"节点之间传什么、谁说了算"（接缝治理），dsh 内核加权限分离治理"系统层面谁能做什么"（系统级治理）。工具/权限这根线从 L1 的"系统注入与工具结果只读"一路走到 L4 的"权限位分离与只读沙箱"，在安全性这个痛点上合流。

还有一块没动，规划推理。目前它靠 prompt engineering 撑着，是这条主线上尚未工程化的最后一块。等自建超级 Agent 或者专门的规划模块时，这条线会再往前推一格。

可靠性不会等模型变强就自动解决。已经有研究开始尝试把 Agent 的失败归因到"模型问题"还是"harness（围绕模型的工程外壳）问题"。比如一篇题为 ["Model or Harness? An Interaction-Centric Taxonomy for Localizing Agent Failures"](https://arxiv.org/abs/2607.28802)的论文（arXiv:2607.28802），从交互视角对 Agent 失败做归因分类。这个区分本身说明，即使模型能力不变，围绕它的工程结构仍然是一个独立的、可以持续优化的变量。[SWE-agent 的实验](https://arxiv.org/abs/2405.15793)更早地证明了这一点，固定基座模型，仅重新设计 Agent-Computer Interface，就能在 SWE-bench 上取得显著提升。把"可靠"工程化，就是承认这件事，然后一层一层地把治理结构搭起来。
